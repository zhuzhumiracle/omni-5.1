## 1. 结论先行（针对“速度变慢 + 学不到东西”）

当前版本出现“奖励短时冲高后归零、success 长时间 0%”并不只是“加了相机”这么简单，而是**多因素叠加**：

1. 模型从原先轻量 MLP（state+lidar）变为三分支 Conv+门控融合（state+KU+depth），计算量明显增加，训练速度变慢是预期现象。
2. 与历史成功实验相比，本次实验配置并非只改传感器：`num_envs` 从 150 改到 10，算法配置还出现了 `policy_mode: spo`，这会显著改变训练动态。
3. 三输入骨干中“深度补全 + 门控”直接在输入层改写 KU（雷达编码）；门控随机初始化时会把真实 KU 与随机补全混合，可能在训练初期污染有效雷达信息。
4. 深度链路调试开关默认关闭（`depth_debug_checks: false`），若出现深度帧空/陈旧，很难第一时间发现。

## 2.4 策略骨干从双输入改为三输入（`test_base_camera+lidar.py`）

原版：`state + lidar(3200)` 的 MLP 编码。  
现版：`state + KU(40x80) + depth(1x96x160)` 的 CNN 门控融合。

核心前向流程：

```python
x_ku_raw = x_ku_flat.reshape(b, 1, 40, 80)
depth = depth_flat.reshape(b, 1, 96, 160)

depth = torch.clamp(depth, 0.0, self.depth_value_max) / self.depth_value_max

# depth -> tokens
depth_feat = self.depth_encoder(self.depth_stem(depth))
depth_tokens = self.depth_token_proj(depth_feat)
depth_aligned = F.interpolate(depth_tokens, size=(40, 80), mode="bilinear", align_corners=False)

# depth 引导补全 KU
ku_logits = self.depth_to_ku(depth_aligned)
completion_ku_norm = torch.sigmoid(ku_logits[:, 0:1])
gate_map = torch.sigmoid(ku_logits[:, 1:2])
completion_ku = completion_ku_norm * self.ku_value_max
refined_ku_raw = gate_map * x_ku_raw + (1.0 - gate_map) * completion_ku

refined_ku_norm = refined_ku_raw / self.ku_value_max
refined_feat = self.ku_encoder(refined_ku_norm)
refined_z_ku = self.ku_global_head(refined_feat)

fused = torch.cat([refined_z_ku, state_2d], dim=-1)
out = self.fusion_mlp(fused)
```

## 4. 逻辑错误/高风险点排查结果

## 4.1 高风险点A：门控融合初期会污染雷达有效信息（最关键）

当前公式：

```python
refined_ku_raw = gate_map * x_ku_raw + (1.0 - gate_map) * completion_ku
```

问题：`gate_map` 和 `completion_ku` 都来自随机初始化卷积层。训练初期 `gate_map` 往往接近 0.5，意味着真实 KU 会被大量随机补全值覆盖，直接降低可学习信号质量。

影响：
- 表现为“能更新（梯度非零），但学不到任务目标”。
- 与你说的“峰值后归零”现象一致。

---

## 4.2 高风险点B：引入大量 BatchNorm2d，在 RL 小批次下不稳定

三输入骨干大量使用 `BatchNorm2d`。在 on-policy RL 场景，样本非IID且每次 batch 统计分布波动大，容易导致特征分布漂移，尤其 `num_envs=10` 时更明显。

---

## 4.3 高风险点C：深度链路可观测性不足

虽然实现里有空帧 fallback（空时填 `depth_max_range`），但本次配置 `depth_debug_checks: false`，无法及时知道深度是否 stale/无效。

如果深度长期接近常量，门控分支学到的会是错误偏置，而不是几何信息。

---

## 4.4 高风险点D：实验配置变化过大，掩盖根因

你当前 run 同时改了：
- 传感器输入（加深度）
- 网络架构（MLP -> CNN+门控）
- 并行环境数（150 -> 10）
- 训练策略配置（出现 `policy_mode: spo`）

这是典型“多变量同时改变”，很难判断到底是哪一项导致退化。

---

## 4.5 已确认不是“完全不训练”问题

日志中 `actor_delta_*` 长期非零，说明参数确实在更新，不是“优化器没绑上”那类硬错误。

## 5. 建议的修复优先级（按收益排序）

1. **先做严格单变量对照实验**：保持算法与超参不变，仅切换 `forest_singal` vs `forest_lc`。
2. **门控保守初始化**：让 `gate_map` 初值接近 1（先信任雷达），避免随机补全污染输入。
3. **减少/替换 BN**：优先换成 GroupNorm/LayerNorm，或先去掉 KU 分支 BN 做消融。
4. **打开深度调试**：`depth_debug_checks=true`，确认 depth 帧不是空/静态。
5. **先简化融合**：先做 `state + ku + depth_global_pool` 的直接拼接基线，再逐步加“补全+门控”。

## 6. 你提到的“雷达未归一化”检查思路，这次复核结果

本次三输入脚本中，KU 与 depth 都做了归一化：

```python
refined_ku_norm = refined_ku_raw / self.ku_value_max

depth = torch.clamp(depth, 0.0, self.depth_value_max) / self.depth_value_max
```

因此“雷达完全未归一化”这一历史问题在当前脚本里已修复。  
当前更大的问题是：**归一化后输入仍可能被门控随机混合破坏**。
